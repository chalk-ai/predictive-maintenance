# Predictive maintenance from fused sensor timeseries

Fuse sensors that report at different rates into one failure-risk score per pump, on Chalk.

Northfield Water is a fictional utility with eight centrifugal pumps. Each pump reports five tags to
a historian, each at its own rate:

| Tag | Unit | Every |
| --- | --- | --- |
| `vibration` | mm/s | 10 s |
| `motor_current` | A | 15 s |
| `shaft_speed` | rpm | 30 s |
| `discharge_pressure` | bar | 30 s |
| `bearing_temp` | °C | 60 s |

Over 48 hours, P-104 develops a bearing fault and trips at hour 44. P-106 runs near full load all day,
so its raw vibration is among the highest in the fleet while it stays healthy. A fused feature,
vibration per unit of load measured by motor current, tells the two apart. On the recorded run the
risk model crossed its alert threshold at hour 29, 15 hours before the trip, and stayed quiet for
every healthy pump.

The pumps and their sensor data are fictional, from a seeded simulator. The features, the queries
and the model all run on Chalk.

## Files

| File | Role |
| --- | --- |
| `pumps/sensors.py` | The seeded sensor simulator: daily demand, load-dependent sensors, an optional bearing fault |
| `pumps/features.py` | `SensorReading` (one historian sample) and `Pump`, which fuses them with windows ending at `_.chalk_now` |
| `pumps/resolvers.py` | Resolvers over the simulated historian (stand-ins for a SQL resolver over your historian table) |
| `pumps/model_weights.py` | The fitted risk and remaining-useful-life models, generated by `train_model.py` |
| `fusion_reference.py` | A numpy reference for the fused features, used for training and parity checks |
| `train_model.py` | Fits the models on a separate simulated fleet of 160 pumps |
| `record_run.py` | One offline query: every pump every 30 minutes for 48 hours, each row as of its own instant |
| `export_page_data.py` | Condenses `results/` into the data behind the demo page |
| `server.py`, `deploy.py` | The live API behind the demo page, deployed as a Chalk ScalingGroup |
| `results/` | The recorded offline query and its parity check |

## How the fusion works

Every sample is a row with a tag, a value and a timestamp. Each fused feature filters a pump's rows to
one tag and a window ending at `_.chalk_now`, so tags sampled every 10 seconds and every minute land on
the same instant:

```python
@features
class Pump:
    id: str
    readings: DataFrame[SensorReading] = has_many(lambda: SensorReading.pump_id == Pump.id)

    vib_rms_1h: float = F.sqrt(_.readings[
        _.value_sq, _.tag == "vibration",
        _.ts > _.chalk_now - timedelta(hours=1), _.ts <= _.chalk_now,
    ].mean())
    current_mean_1h: float = _.readings[
        _.value, _.tag == "motor_current",
        _.ts > _.chalk_now - timedelta(hours=1), _.ts <= _.chalk_now,
    ].mean()

    load_frac_1h: float = _.current_mean_1h / RATED_CURRENT_A
    vib_per_load_1h: float = _.vib_rms_1h / F.greatest(_.load_frac_1h, 0.3)
```

`_.chalk_now` is the wall clock in an online query and each row's input time in an offline query, so
the same definitions serve live scoring and leak-free replays. The risk model is a scikit-learn
logistic regression written out as a native Chalk expression (`F.sigmoid(...)` over the fused
features), so there is no separate model server.

## Run it

You need [`uv`](https://docs.astral.sh/uv/) and a Chalk environment.

```bash
chalk apply --branch predictive-maintenance     # the historian, fused features and model
./record_run.py # the fleet every 30 minutes for 48 hours
chalk query --branch predictive-maintenance --in pump.id=P-104 \
  --out pump.failure_risk_12h --out pump.vib_per_load_1h --now 2026-10-11T12:00:00Z
```

`record_run.py` also checks Chalk's features against `fusion_reference.py`. On the recorded run they
agree to within 1e-10.

To retrain the models, run `./train_model.py`. It rewrites `pumps/model_weights.py`.

## The live API

`server.py` answers `GET /api/at?pump=P-104&minute=2160` with a Chalk online query whose `now` is that
minute of the recorded window, and `GET /api/raw` with the raw samples of the 10 minutes before it.
It uses a service token that can only run online queries; see `deploy.py` for how to create it,
store it as a Chalk secret, and deploy the API as a ScalingGroup.

## Local authentication

The SDK reads credentials, API host, and the selected environment from your existing
`chalk login` in `~/.chalk.yml`, including project-scoped and default logins.
For unattended runs, `CHALK_CLIENT_ID` and `CHALK_CLIENT_SECRET` remain supported.
The examples use the current environment selected by your Chalk login.

Requires `chalkcompute>=2.13.8` with the public connection context and in-memory
secret APIs from [chalk-sandbox-sdk#511](https://github.com/chalk-ai/chalk-sandbox-sdk/pull/511).
This PR is waiting for that SDK release.
